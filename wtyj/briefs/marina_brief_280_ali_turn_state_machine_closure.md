# BRIEF 280 — Ali turn state machine closure
**Status:** Approved | **Files:** `wtyj/agents/marina/marina_agent.py`, `wtyj/agents/social/ali_quote_workflow.py`, `wtyj/agents/social/social_agent.py`, `wtyj/agents/social/webhook_server.py`, `wtyj/agents/social/zernio_dm_client.py`, `wtyj/agents/social/senders/base.py`, `wtyj/agents/social/senders/__init__.py`, `wtyj/agents/social/senders/zernio.py`, `wtyj/tests/agents/test_ali_quote_workflow.py`, `wtyj/tests/agents/test_ali_quote_intake_dispatch.py`, `wtyj/tests/agents/test_ali_latest_change_orchestration.py`, `wtyj/tests/social/test_message_reliability_p0.py`, `wtyj/tests/test_zernio_confirmed_reply.py` | **Depends on:** Briefs 271, 275, 276, 279; GitHub issue #195 | **Blocks:** GitHub issue #198

## Context
PR #197 fixed the immediate recommendation-versus-summary priority inversion, but production still persists `awaiting_quote_confirmation` before Zernio confirms that the summary was delivered. The current flags also remain eligible after Carlos answers a question or sends a recommendation, so a later bare “yes” can confirm an older rejected summary. Quote workers sleep through the three-minute customer boundary without rechecking whether a newer customer change superseded the old customer delivery. Issue #195 therefore remains open: the permanent closure needs one plan per inbound turn, delivery-anchored summary eligibility, and a customer-delivery supersession guard while preserving immutable pricing, PDF, and staff work.

## Why This Approach
Add one optional structured primary Ali intent to Marina’s existing single Claude response, then let Python build one `AliTurnPlan` with one outbound kind. Persist canonical draft state before sending, but commit presented-summary eligibility and last-delivered kind only after the provider accepts the outbound action. Quote rows gain additive customer-delivery supersession metadata, and the worker rereads it after the delay and immediately before each customer asset. Rejected alternatives were extending the existing booleans (which leaves ambiguous precedence), parsing reply text in Python (forbidden and multilingual-fragile), and cancelling/deleting immutable quote snapshots (breaks auditability).

## Instructions
1. Extend `marina_agent.py`’s forced tool schema and Ali prompt with one optional `ali_primary_intent` enum: `continue_intake`, `ask_question`, `reject_or_hesitate`, `request_recommendation`, `repeat_summary`, `confirm_summary`, `other`. Keep `ali_rental_change` independent and keep one Claude call.
2. In `ali_quote_workflow.py`, add explicit phases (`COLLECTING`, `DISCOVERY`, `SUMMARY_PRESENTED`, `QUOTE_PROCESSING`, `QUOTED`, `ESCALATED`) and an `AliTurnPlan` carrying exactly one outbound kind, safe reason metadata, current draft/presented hashes, summary version, and action id. Build the plan in the required order: validated change, human escalation, recommendation, question/rejection, explicit repeat, guarded confirmation, initial/corrected summary, otherwise model reply.
3. Treat confirmation as valid only when deterministic parsing accepts it, the phase is `SUMMARY_PRESENTED`, the current draft hash equals the delivered presented hash, and the last provider-confirmed kind is `summary`. A successfully delivered non-summary action clears presented-summary eligibility. Keep legacy flags only as compatibility projections, not as decision authority.
4. Return plan commit metadata from `social_agent.py` without marking a summary presented. Preserve the existing recommendation builder and catalog validation. A valid recommendation remains mutually exclusive with a summary, and a failed recommendation validation falls back to the model’s clarification rather than a stale summary. If Marina emits a valid recommendation but omits only its independent vehicle-change patch, deterministically derive the safe selection context from those already validated catalog options: one specific option selects that vehicle, curated options from one class select that class, and mixed options clear the stale selection while discovery continues.
5. In `webhook_server.py`, derive one opaque action id from the inbound provider ids. Send ordinary Ali text through the shared sender with provider status confirmation and the action id as its retry-safe Zernio idempotency key; keep the existing idempotent recommendation transport. Only after provider-confirmed success, atomically commit the Ali delivered kind and summary/recommendation marker, then store the assistant timeline and complete the inbound event. On provider failure, do not create summary eligibility or a delivered marker.
6. Add additive supersession columns to `ali_quotes`. When a validated change or explicit alternative exploration follows a pending quote, mark only its customer delivery superseded. Preserve its pricing, PDF, staff email, and operator audit. In `process_quote()`, reread the row after the remaining delay and immediately before brand-card/PDF sends; skip superseded customer assets without escalation.
7. Version each newly presented draft so A → B → A creates a new immutable quote rather than reusing an older snapshot. Recommendation delivery markers and Zernio idempotency keys are scoped to the inbound action id: replays of that action produce no fallback text or duplicate media, while a later explicit request has a new action id and may intentionally resend the same catalog recommendation.
8. Log only phase, primary intent, outbound route, reason, changed field names, and hash/id prefixes. Never log message text, customer data, dates, locations, or full identifiers.

## Tests
1. Table-drive phases against all seven primary intents and assert exactly one outbound kind, with recommendation/question/rejection outranking automatic summary and guarded confirmation requiring the provider-delivered current summary.
2. Exercise the social-agent plus provider-success boundary: summary send success enables confirmation; summary send failure does not; price/discovery/rejection/recommendation success suspends old confirmation; a later bare yes creates no quote until explicit summary re-presentation.
3. Run the reported Ertiga/SUV chain through correction, recommendation, rejection, exact choice, corrected summary, confirmation, and replay; assert one visible action per turn and one quote. Repeat the combined SUV/media turn with an intentionally omitted `ali_rental_change` and prove the catalog-grounded recommendation fallback cannot retain Ertiga.
4. Cover every #190 field change, EN/NL/PAP/DE state parity, explicit repeat, question during `QUOTE_PROCESSING`/`QUOTED`, recommendation replay versus a new request, and sanitized transition logs.
5. During the three-minute window, apply a newer change and assert staff/PDF work remains auditable while both old customer assets are skipped. Cover already-delivered replacement and A → B → A immutable versioning.
6. Run the focused Ali workflow/intake/orchestration/reliability files, then `python3 -m pytest wtyj/tests/ -q` with zero failures.

## Success Condition
Production accepts confirmation only for the latest provider-delivered current summary, sends at most one planned action per inbound turn, and suppresses a superseded quote’s customer assets while preserving immutable staff/audit work.

## Rollback
Revert the Brief 280 source commit and redeploy the prior image through the normal WTYJ pipeline. The database additions are nullable/additive and may remain; rollback code ignores them. If a canary exposes a delivery regression, disable Ali customer delivery first, preserve staff/PDF processing, then restore the prior image and re-enable only after health checks.
